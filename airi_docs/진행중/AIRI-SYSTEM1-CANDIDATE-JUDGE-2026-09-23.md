## 0. 결론

1. **응답 시간을 잡아먹던 것은 프록시 재생성이 아니라 평가 하네스의 "후보 16개 생성 + 규칙 점수 선택"이었다.**
   운영 경로(local-quality-probe)에서 프록시 재생성은 544회 중 0회였고, 반응 부분이 턴 시간의 83%였다.
2. **그 규칙 점수(`slot_candidate_score`)는 시청자 채팅 단어를 많이 베낄수록 높은 점수를 준다.** 그래서 16개 중
   가장 많이 따라 말한 후보를 골랐다. 첫 합격 후보에서 멈추기만 해도 빨라지고 좋아진다.
3. **System1(0.5B 판정기)은 두 판정자 모두에서 규칙 방식보다 높았고, 독립 판정자 기준 차이는 +15%p다
   (기준값 0.6).** 대신 규칙 방식보다는 느리다. 사람 채점은 아직 없다 — 블라인드 검토 페이지를 만들어 두었다.
4. **8 GB 모델 교체:** Mi:dm 이후 새 버전은 없다. A.X-4.0-Light(Apache-2.0)는 같은 선택 방식에서 Mi:dm보다
   5~12%p 높지만 약 2배 느리다. Kanana-1.5-8B(Apache-2.0)는 낫지 않았고 원방송 경험 도용 바닥 지표를 매 회 1턴 어겼다.
5. **운영 위험 발견:** Ollama 0.34.2는 Modelfile TEMPLATE 대신 GGUF 내장 Mi:dm 템플릿을 쓰며, 매 요청에
   "Mi:dm은 KT에서 개발한 AI 기반 어시스턴트", "기본적으로 경어체를 사용해야 한다"는 약 500토큰을 끼워 넣는다.

> **추가 주의 (사용자 지적으로 확인):** 이 32턴 시나리오는 설정이 서로 충돌한다. 지문(plot·beat)과 시나리오의 시청자 채팅(작성된 문장 — 실제 채팅 기록 5,243건에 0/32건 존재)은
> **방송인 본인이 아픈 상황**을 전제하는데("방송 중에도 신경 쓰일 만큼", "병원 바로 간 건 잘했어", "이번엔 쉬어야지"),
> 러너 지시·슬롯 큐·스파인은 이를 3인칭 "그 사람" 이야기로 말하게 강제한다. 입력 형식도 작성자 없는 1대1 대화다.
> 모델은 이 모순을 "아픈 건 시청자"로 풀어 조언·주체 전도를 만든다. 교사 기준도 같은 3인칭 가정을 따랐으므로,
> 이 문서의 수치는 **이 시나리오 위에서의 선택 방식 간 상대 비교**로만 유효하다.

**원인 분리 — 2회차 대화 고정 재실행** (턴 N에 2회차의 1..N-1 히스토리·같은 채팅·같은 브리핑, shim에서 프록시 프롬프트 캡처,
llama-server 직접 재생성, 턴별 핵심어 판정 — 2회차 실제 답에서 9/23로 AI 판독과 일치):

- 라이브 receipt는 메모리 저널(durable)을 요구한다. 메모리를 끄면 첫 receipt가 400이 되고, 한 쇼에 진행 중 턴이 하나만
  허용돼 이후 모든 턴이 브리핑 없이 일반 대화로 처리된다(1/24). 운영에서 receipt 한 번 실패의 파급을 확인할 가치가 있다.
- 프롬프트에서 브리핑과 시청자 채팅 사이에 1대1 질문응답 지시("질문에 먼저 답해", "사용자 말에 없는 사실은 만들지 마")가
  끼어 있지만, **Mi:dm은 배치·머리말을 바꿔도 무반응**: 28·28·27·29/69, 6회 표본 54·54·53/138.
- **A.X-4.0-Light는 머리말 강화에 반응**(43 → 54/69)하나 답이 길고(중앙 100자) 시청자에게 되묻고 괄호·라벨이 샌다.
  단독 약 4.5 GB VRAM — 기록된 전체 스택(Mi:dm급 LLM + TTS + STT) 7,786 MiB에 비춰 8 GB 동거는 어려울 전망(**미실측**).
- **후보 선택**: 「이번 턴에 말할 것」 줄의 글자 2-gram 커버리지로 고르면 Mi:dm 한 번 9.0/23 → 6개 중 16/23. 다만 스태프 메모
  문장을 그대로 베낀 답("먹었다.", "운만 뗀다")이 뽑혀 거름 조건(존댓말·글말 어미·라벨)을 넣으면 13/23. 브리핑을 AIRI가 실제로
  할 반말 문장으로 쓰면 베껴도 자연스러워 **15/23, 부적합 선택 0, 커버리지 0.3 조기 종료 시 평균 2.96회 생성**.

**3회차에서 새로 드러난 문제**

1. 브리핑을 100% 담은 이야기 답이 「아, 그게...」로 시작해 출력 경계에서 두 번 비워지고 침묵 대체문 「음, 잠깐만.」이
   나갔다(T15, 위 경로 정정 참조). 저장된 Mi:dm 후보 552개 중 16개가 이렇게 비워지고 그중 12개가 말줄임표 때문이다.
2. 하지 않은 검색과 실존 작품 거짓 사실(T21 "검색해봤는데 … 도라에몽 '도라미'래")이 그대로 나갔다.
3. 후보 6개가 모두 채팅 전제("좀 나아짐?", "어디 갔는데?")를 따르면 선택으로도 못 고친다(T07·T20).
4. 「아, 그래서」로 시작하는 말버릇 6턴(2회차 1턴).
5. 지연: 중앙 667 ms, p90 1.7 s, 최대 2.3 s(후보 평균 2.6개, 순차 생성).

**구현 (로컬 미커밋, 기본 꺼짐)** — 판정 규칙 `ollama-proxy/live_briefing_select.py`
(`AIRI_LIVE_BRIEFING_CANDIDATES` 2~6, `AIRI_LIVE_BRIEFING_COVERAGE` 기본 0.3; 부적합 = 존댓말·글말 어미, 라벨 누출, 하지 않은
조회 주장, 직전 답과 20자 이상 반복; `/health`의 `live_briefing_select`), 테스트 `test_live_briefing_select.py`와
`test_ollama_proxy.py` 라우트 테스트 6개. native `/api/chat` 두 경로와 `/v1` 스트리밍 경로에 연결했다. `/v1`에서는 켜져 있을 때
첫 문장 조기 송출을 보류하고, 기억 부재 즉답과 일대일 교정 재시도·대체문 연쇄를 건너뛰며, 고른 답의 문장을 한 번에 보낸다.
브리핑 줄 `- 이번 턴에 말할 것:`이 이 기능을 켜는 관례이며 없으면 아무 일도 하지 않는다. 5회차 뒤 「직전 답과 같은 첫 두 단어」
거절 규칙은 뺐다 — 「아, 그래서」 말버릇이 모든 재생성에서 유지돼 예산만 소모했다(T23 6회 생성, 1.95 s).

**4~5회차가 보여 준 앱 경로 문제**: 조기 송출 뒤 나머지 문장을 버려 이야기 사실이 둘째 문장에 있으면 사라진다(4회차 T21
「진짜 미친 거 같았어.」). 일대일용 코드 답이 방송에서 오작동했다 — 「그래서 이름이 뭔데」→ 「아직 기록이 없어. 어떻게 부르면
돼?」(기억 부재 즉답), 「어제 저녁은 뭐 먹었어?」→ 「든든하게는 김치찌개나 덮밥…」(질문 근거 검사 뒤 식사 대체문).

**지연과 System1(사용자 지시: "음성지연의 경우 jev를 도입해보자")** — 이 PC 실측(Mi:dm, llama-server, 저장된 방송 프롬프트 12개):
- 같은 프롬프트 재생성은 프롬프트를 재사용한다(평가 토큰 1): 1회 363 ms, 2회 237 ms, 3회 180 ms(중앙). 슬롯 3개 동시 생성은
  597 ms(단일 309 ms)에 GPU +1.5 GB라 이득이 없다. ⇒ 지연의 본체는 판정이 아니라 추가 생성(회당 약 0.2 s)이다.
- 첫 문장만으로 전체 답의 합격을 맞히는 힘이 약하다: 글자 2-gram AUC 0.65~0.69, KURE-v1 의미 유사도 0.66~0.69, 전체 답
  0.81~0.88. 사실이 둘째 문장에 오는 일이 많아서다. ⇒ 첫 문장에서 미리 결정하는 판정기는 학습해도 상한이 낮을 전망이다.

**6회차 — 사용자 선택 「후보 3개 + 모두 탈락 시 브리핑 문장 그대로」** (`select_candidate`가 넷째 값으로 알림; 브리핑 문장이
같은 부적합 규칙을 통과할 때만 말하므로 스태프 메모체 「…먹었다.」는 읽지 않는다; `/health`에 `briefing_line_spoken`):
턴당 생성 1.9회(5회차 3.4), 대사 도착 중앙 590 ms·p90 823 ms·최대 1,073 ms(5회차 1,017·1,952·2,334), 깨끗한 턴 약 18/24.
전제 질문(「좀 나아짐?」)·빈칸 질문(「어디 갔는데?」)이 브리핑 문장으로 정확히 나갔고 결말·마무리가 처음으로 끝까지 전달됐다.
남은 오류는 글자 겹침이 잡지 못하는 의미 오류다 — T10 위치 바뀜(입천장 → 귀 안쪽), T13 「방송 끝나고 목캔디 사 먹을 거야」(이미
샀음). 의미 대조는 System1이 맡을 수 있는 다음 후보다(판정 비용 수십 ms, 지연 영향 작음).
