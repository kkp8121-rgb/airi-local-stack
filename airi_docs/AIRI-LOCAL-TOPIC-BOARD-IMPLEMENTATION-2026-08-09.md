# AIRI local topic board implementation

## Runtime boundary

- The board is OFF unless `AIRI_TOPIC_BOARD_PATH` is explicitly configured.
- `start-local-ollama-proxy.ps1 -TopicBoardPath ...` accepts only a regular file under `ollama-proxy/runtime`.
- Before a configured proxy is reused or started, the launcher runs `validate_approved_topics.py` with its selected Python interpreter. The offline validator accepts only schema v2, validates the local runtime path, loader safety, and freshness, and requires at least one live approved item.
- The validator makes no network, model, service, or write call. Its output is content-free JSON containing only `status` and `live_approved_count`. `status=valid` means already-approved records are runnable; the validator never grants approval.
- Automatic fetching, RSS polling, external search, cloud chat, cloud search, extraction, and evaluation collection are not enabled by this feature.

## File contract

`ollama-proxy/approved-topics.example.json` documents only the empty root shape. Do not copy and fill it by hand; the reviewed compiler creates the operational file under `ollama-proxy/runtime`.

```json
{
  "schema_version": 2,
  "approval_workflow_version": 1,
  "items": []
}
```

Every live `approved: true` item needs bounded safe metadata plus a `broadcast_line`. `broadcast_line` is the exact, explicitly preapproved Korean sentence delivered for that item. The model does not generate that spoken line. Schema v1 is rejected because it lacks this delivery field. Runtime schema-v2 boards must also have exact root `approval_workflow_version: 1` and per-item pending/approval provenance; manual `approved: true` JSON is rejected.

Do not hand-author runtime items. Use the pending JSONL, human decision sidecar, and deterministic compiler documented in `ollama-proxy/topic-review/README.md`; the compiler supplies the required provenance and approval objects.

The deterministic offline compiler is the only supported runtime-board producer. It binds canonical pending and human-decision hashes, then the loader reconstructs and verifies both records before accepting an item. These hashes preserve local human-governance provenance; they are not signatures or independent proof of source truth. The loader requires an absolute local file, no more than 256 KiB, at most 64 items, valid IDs, safe bounded text, and a live expiry later than publication. One invalid approved item fails the board closed.

Legacy or hand-authored schema-v2 boards without this binding are not migrated automatically. Keep them inactive; recreate their records as pending JSONL, review them explicitly, and compile a new board if they are still wanted.

## Delivery and persistence

- Raw board metadata remains transient and never enters memory SQLite, character state, extraction, or evaluation storage.
- The only deliverable sentence is the preapproved `broadcast_line`; no topic speech is generated by the model.
- A topic enters the bounded in-process recent set only after a non-empty terminal response is consumed.
- `delivered=true` currently means the proxy's HTTP terminal response was consumed; it is **not** a TTS playback acknowledgement. Playback ACK remains a separate follow-up integration.
- While a proactive request is active, its topic has an in-process lease. Concurrent requests cannot reserve the same item; failed or stale mappings release the lease without advancing its recent-cycle state.
- `/health.topic_board` exposes only content-free counters and status; it does not expose a path, ID, title, source, summary, or broadcast line.

## Operational default

The default launch keeps the path empty. This preserves the explicit human approval boundary.
